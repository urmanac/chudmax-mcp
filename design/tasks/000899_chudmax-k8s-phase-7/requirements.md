# Requirements: chudmax k8s phase 7 Flagger canary rehearsal in CI

> **Public mirror** — the full-fidelity record (including deployment specifics) lives in the private source-of-truth repo.

T-0037 phase 7 (`kubernetes/phases.md`; source `design/tasks/000888_fetch-mr-17/design.md`, SPIKE row G "Canary rehearsal"): **in CI, one web upgrade is promoted by Flagger after its tests pass, one broken upgrade is rolled back, and both are recorded.** Flagger shifts traffic on an HTTPRoute 10% at a time to 50%; a pre-rollout webhook checks `/health`, `/mcp` tool counts and one short chat end-to-end; the ticket server's selftest questions are asked through the canary before promotion; both versions share the one engine so test traffic stays small. This is the largest rehearsal in the plan — the spike's Open Question 2 asked whether to split it; **kept as one card** unless the human says otherwise (Open Questions). Depends on phase 6 (merged). The **Gemini planning brief (2026-11-26) is folded in**: the phase-9 parallel boundary (Hermes chart — disjoint write sets, both directions), the `STRATA_ALLOWED_HOSTS` coverage of Flagger's generated Service names (the DNS-rebinding guard would 403 them otherwise), Fable's two phase-6 polish fixes riding the same umbrella tree, and the standing fact that **kindnet has enforced NetworkPolicy since kind v0.24**. The **owner pointer (2026-11-26) is folded in too**: the metric dimension is REAL but lightweight — Flagger's built-in single-pod Prometheus, with the metricsServer URL values-configurable and the MetricTemplate/ServiceMonitor/PodMonitor shape kept drop-in compatible with the `fluxcd/flux2-monitoring-example` / Cozystack kube-prometheus-stack pattern for phase 15 placement. The **coordination note (2026-11-26) is folded in as well**: (a) a dedicated monitoring card owns `k8s/monitoring/**` + `.github/workflows/monitoring-validate.yml` — this card stays STRICTLY out of both; (b) install-flux's chosen Gateway API controller (ADR 001) is **Traefik** (`providers.kubernetesGateway.enabled=true`, metrics on :9100) — the rehearsal aligns with the production choice instead of the tutorial's Istio; (c) Strata's `terminal/serve/prometheus.py` exposes **native Prometheus OpenMetrics** on `GET /metrics?format=prometheus` — the canary's metric source.

## User stories

1. **As the human**, I want the canary rehearsal to prove Flagger promotes a good web upgrade hands-off: the pre-rollout suite (health, tool counts, chat, selftest questions) passes, the weight steps 10→50 are recorded, and the promotion is receipted by canary status/events.
2. **As the human**, I want the broken upgrade caught by the SAME gate: a canary whose hub config points at an unreachable server (the verified silent-omission behavior — no ticket tools) fails the pre-rollout webhook, Flagger halts and rolls back, and the weight never leaves the primary — both upgrades' records side by side.
3. **As the rehearsal**, I want both versions wired to the ONE tickets-mcp Service through the same mounted `--mcp-config` (the hub's URL mode — the spike's settled question) and both running `--engine mock`, so the canary upgrade touches only the web image and test traffic stays small (the probes, the pre-rollout suite, and ONE tutorial-scale loadtest stream at ~10 rps through the gateway).
4. **As the rehearsal**, I want the mcp Service serving real data — the phase-5 artifact chain ships one seed ticket so the selftest questions asked through the canary return the published-contract answers, not no-data stubs.
5. **As CI**, I want `canary-kind.yml` to re-prove everything hands-off: the sandbox-style pre-flight (hub ↔ canonical-server integration AND the Strata metrics surface — a chat turn increments `vllm:request_success_total` and fills the e2e histogram), lint/template/kubeconform, the image builds, and the kind rehearsal whose receipts (HTTPRoute weight timeline, promotion + rollback events, suite outputs, and the REAL metric receipts — a Prometheus instant-query showing the strata counter/histogram data flowing during the loadtest) land in the step summary.
6. **As the human**, I want the standing hygiene: box untouched, no registry push, no LAN address/credential/internal hostname in any public artifact, three labels on every claim, conventional commits, merge authority CoS.

**Web chart wiring (`k8s/umbrella/chudmax/subcharts/chudmax-web/`)**
- [ ] A `web.mcpConfig` knob (object, default unset): renders an inline ConfigMap, mounts it at a fixed path and appends `--mcp-config <path>` — the config lives in the Deployment **template**, so both Flagger versions (primary and canary) inherit it automatically.
- [ ] A `service.enabled` knob (default true): the canary install turns it OFF — Flagger generates its own `<name>`/`<name>-canary`/`<name>-primary` Services and the chart's same-named Service would collide; the Helm test hook renders only when the Service does.
- [ ] A `podAnnotations` passthrough (map, default `{}`): the rehearsal sets the scrape annotations (`prometheus.io/scrape: "true"`, `prometheus.io/port: "8080"`, `prometheus.io/path: "/metrics?format=prometheus"`) on BOTH versions' pods (the Deployment template again) so Flagger's tiny Prometheus scrapes Strata's native metrics — the same endpoint the monitoring card's PodMonitor will select in phase 15.
- [ ] `helm lint` + `helm template` ×2 (defaults byte-identical to phase 6; a variant with `mcpConfig` set + service off) + kubeconform -strict — locally and in CI.
