# Requirements: chudmax k8s phase 7 Flagger canary rehearsal in CI

> **Public mirror** — the full-fidelity record (including deployment specifics) lives in the private source-of-truth repo.

T-0037 phase 7 (`kubernetes/phases.md`; source `design/tasks/000888_fetch-mr-17/design.md`, SPIKE row G "Canary rehearsal"): **in CI, one web upgrade is promoted by Flagger after its tests pass, one broken upgrade is rolled back, and both are recorded.** Flagger shifts traffic on an HTTPRoute 10% at a time to 50%; a pre-rollout webhook checks `/health`, `/mcp` tool counts and one short chat end-to-end; the ticket server's selftest questions are asked through the canary before promotion; both versions share the one engine so test traffic stays small. This is the largest rehearsal in the plan — the spike's Open Question 2 asked whether to split it; **kept as one card** unless the human says otherwise (Open Questions). Depends on phase 6 (merged).

## User stories

1. **As the human**, I want the canary rehearsal to prove Flagger promotes a good web upgrade hands-off: the pre-rollout suite (health, tool counts, chat, selftest questions) passes, the weight steps 10→50 are recorded, and the promotion is receipted by canary status/events.
2. **As the human**, I want the broken upgrade caught by the SAME gate: a canary whose hub config points at an unreachable server (the verified silent-omission behavior — no ticket tools) fails the pre-rollout webhook, Flagger halts and rolls back, and the weight never leaves the primary — both upgrades' records side by side.
3. **As the rehearsal**, I want both versions wired to the ONE tickets-mcp Service through the same mounted `--mcp-config` (the hub's URL mode — the spike's settled question) and both running `--engine mock`, so the canary upgrade touches only the web image and test traffic stays small (probes + the pre-rollout suite, no gateway load).
4. **As the rehearsal**, I want the mcp Service serving real data — the phase-5 artifact chain ships one seed ticket so the selftest questions asked through the canary return the published-contract answers, not no-data stubs.
5. **As CI**, I want `canary-kind.yml` to re-prove everything hands-off: the sandbox-style pre-flight (hub ↔ canonical-server integration), lint/template/kubeconform, the image builds, and the kind rehearsal whose receipts (HTTPRoute weight timeline, promotion + rollback events, suite outputs) land in the step summary.
6. **As the human**, I want the standing hygiene: box untouched, no registry push, no LAN address/credential/internal hostname in any public artifact, three labels on every claim, conventional commits, merge authority CoS.

## Acceptance criteria

**Write set and boundaries (hard)**
- [ ] Phase 7 touches only `k8s/canary/**` (new), `.github/workflows/canary-kind.yml` (new) and the web subchart's mcpConfig wiring (`k8s/umbrella/chudmax/subcharts/chudmax-web/**` — additive, default-neutral). `k8s/chart/`, `k8s/rehearsal/`, `k8s/repo-sync/` are consumed **read-only by path** from merged main; no root-README changes.
- [ ] The chart wiring renders **nothing** when `mcpConfig` is unset and the new `service.enabled` knob (default true) changes no default render — proven by template-diff receipts.
- [ ] Phase 8 (image automation) may run in parallel — its write set (`k8s/image/**`, its workflow) is disjoint from this card's.

**Web chart wiring (`k8s/umbrella/chudmax/subcharts/chudmax-web/`)**
- [ ] A `web.mcpConfig` knob (object, default unset): renders an inline ConfigMap, mounts it at a fixed path and appends `--mcp-config <path>` — the config lives in the Deployment **template**, so both Flagger versions (primary and canary) inherit it automatically.
- [ ] A `service.enabled` knob (default true): the canary install turns it OFF — Flagger generates its own `<name>`/`<name>-canary`/`<name>-primary` Services and the chart's same-named Service would collide; the Helm test hook renders only when the Service does.
- [ ] `helm lint` + `helm template` ×2 (defaults byte-identical to phase 6; a variant with `mcpConfig` set + service off) + kubeconform -strict — locally and in CI.

**Canary fixtures (`k8s/canary/`)**
- [ ] Gateway API CRDs installed; a Gateway in the release namespace referenced by `spec.service.gatewayRefs` (same namespace — no cross-namespace ReferenceGrant); **no MetalLB by default** — nothing dials the Gateway, the suite targets the Services directly (the fallback ladder is recorded in design.md).
- [ ] A Canary CRD on the web Deployment: port 8080 / targetPort http; `analysis` with interval, threshold, `maxWeight: 50`, `stepWeight: 10`; ONE always-passing MetricTemplate (`vector(1)`) whose provider address points at a tiny canned Prometheus responder (the phase-5 dummy-sink pattern); and the pre-rollout webhook whose bash suite checks: `/health` → 200; `GET /v1/mcp/tools` **byte-equal between primary and canary** with the namespaced ticket tools present; one short chat turn returning the scripted MockEngine reply; the selftest question set (all seven tools) asked through the canary — data tools asserted against the seed ticket (the id discovered dynamically from `list_tickets`), read-only tools asserted non-empty — with retry loops bounded under the webhook timeout.
- [ ] The rehearsal values profile: `engine.enabled: false`, `web.service.enabled: false`, `web.allowedHosts` an explicit list including the Flagger-generated Service names, `web.mcpConfig` pointing the hub at `http://chudmax-mcp:8080/mcp`.
- [ ] `canary-rehearse.sh`: kind up (the phase-5 kind-config by path) → Cilium (the phase-5 recipe) → flux install with source-watcher → images built + `kind load image-archive` (chart-default tags, no registry) → the umbrella installed with the rehearsal profile → the phase-5 artifact chain applied → one seed push → mcp pod Ready, Service serving → Flagger + loadtester + Gateway + canned Prometheus installed → the **good upgrade** (image retagged `0.1.1` → suite passes → weight 10→50 → promotion recorded) → the **broken upgrade** (one combined kubectl patch: image retagged `0.1.1-broken` + the `--mcp-config` arg swapped to a mounted broken config whose server URL is unreachable → the hub silently omits it → the webhook fails → halt → rollback recorded) → HTTPRoute weights sampled at every step → teardown.
