# Design: chudmax k8s phase 7 Flagger canary rehearsal in CI

> **Public mirror** — the full-fidelity record (including deployment specifics) lives in the private source-of-truth repo.

One kind cluster in one CI job rehearses both halves of the Flagger story: a promoted upgrade and a webhook-caught rollback, over the SAME target deployment, with the canonical tickets-mcp serving real data behind it. The spike's two open mechanics are settled by prior phases: the McpHub accepts servers by URL (verified against the public fork), and the ready-gated mcp Service path needs the artifact chain (verified by phase 5).

## Shape (kind rehearsal)

```
CI job (GitHub-hosted ubuntu runner — the phase-5/6 pattern)
  runner side: gittestserver (Smart HTTP, k8s/rehearsal/gittestserver by path)
      ▲ one git push (the seed ticket)
  kind cluster (k8s/rehearsal/kind-config.yaml by path; Cilium per the phase-5 recipe)
    ns flux-system: source-watcher (flux v2.10.1) ──► ExternalArtifact chudmax-tickets
    ns chudmax:
      ├─ mcp pod: fetcher + canonical server
      │     fetcher unpacks → /data/current → pod READY → Service chudmax-mcp:8080 serves
      ├─ web Deployment chudmax-web (--engine mock, --mcp-config /etc/strata/mcp-config.json)
      │     hub ──► http://chudmax-mcp:8080/mcp   (namespaced tickets__* tools)
      ├─ Flagger (ns flagger, meshProvider=gatewayapi:v1):
      │     <name>-primary Deployment; <name>/<name>-canary/<name>-primary Services;
      │     HTTPRoute chudmax-web (weighted backendRefs — the 10%→50% stepping surface)
      ├─ Traefik (the ADR-001 controller; providers.kubernetesGateway.enabled=true)
      │     provisions GatewayClass traefik; Gateway chudmax-gateway (gatewayClassName:
      │     traefik; referenced by gatewayRefs); its own metrics on :9100 (scraped for receipts)
      ├─ Flagger (ns flagger, meshProvider=gatewayapi:v1, prometheus.install=true):
      │     <name>-primary Deployment; <name>/<name>-canary/<name>-primary Services;
      │     HTTPRoute chudmax-web (weighted backendRefs — the 10%→50% stepping surface)
      │     pre-rollout webhook ──► loadtester pod (ns chudmax): bash suite —
      │        /health 200; /v1/mcp/tools byte-equal primary↔canary + tickets__* present;
      │        one chat turn (scripted MockEngine reply); the seven selftest questions
      │     load-test webhook ──► hey POST chat completions ~10 rps -host <route-host>
      │        ──► traefik svc (in-cluster) ──► the canary's MockEngine finishes them
      │     CUSTOM MetricTemplates (strata-native) ──► flagger's single-pod Prometheus:
      │        vllm:request_success_total finish-rate + vllm:e2e_request_latency_seconds p99
      │        (web pods annotation-scraped on /metrics?format=prometheus, 5s interval)
      └─ no MetalLB; no kube-prometheus-stack/Grafana (the monitoring card owns that stack;
            phase 15 repoints canary.metricsServer at it and flips flagger's serviceMonitor)
```

Traffic in the rehearsal: kubelet probes + the pre-rollout suite + ONE chat-completions loadtest stream (~10 rps through the gateway) — "test traffic stays small" holds; and that stream is load-bearing: only chat turns FINISH engine requests, so without it the finish-rate query returns empty and Flagger treats no-data as failed checks.

## Key decisions

1. **The promoted upgrade is a tag-swap on the chart's default image.** The umbrella installs `ghcr.io/urmanac/chudmax/web:0.1.0` (loaded, `IfNotPresent`); `kubectl set image ...web=...:0.1.1` (same bytes, retagged — the phase-6 build is the one image; no rebuild) triggers Flagger's revision detection. The pre-rollout suite passes → weight steps 10→50 → Flagger copies the template to `<name>-primary` and promotes. One `kubectl` call, one revision.
2. **The broken upgrade rides the VERIFIED failure mode: the hub silently omits a server that fails to start.** The rehearsal applies a second, well-formed ConfigMap (`mcp-config-broken.yaml`) whose server URL is unreachable, and ONE combined JSON patch swaps the image tag (`0.1.1-broken`, same bytes — receipt legibility) AND the `--mcp-config` arg to the broken path. The canary pod stays Ready (`/health` fine — probes pass), so the pre-rollout webhook RUNS and gates: `GET /v1/mcp/tools` returns no `tickets__*` tools → count assert fails → Flagger halts advancement → threshold reached → "Canary failed! Scaling down" — the weight never leaves the primary. A nonexistent-config-path variant was rejected because the config-load-failure behavior (silently empty vs crash-loop) is UNVERIFIED — a crash-looping canary would be caught by the progress deadline, not by the webhook gate, which is the weaker story. A port-drift variant (args `--port 8081`) was rejected for the same reason: the readiness probe, not the webhook, would catch it.
3. **The `--mcp-config` args index is derived from the rendered template, never hard-coded** — the script greps the rendered args list for the config path's position before building the JSON patch (the chart may grow args later).
4. **REAL, app-native metrics — the owner pointer + the coordination note (2026-11-26), superseding both earlier drafts (the canned stub, then the Istio tutorial templates).** The metric SOURCE is Strata itself: `terminal/serve/prometheus.py` serves native OpenMetrics at `GET /metrics?format=prometheus` (verified against the pinned source) — `vllm:request_success_total` (the finished-requests counter, labeled `model_name`), the `vllm:e2e_request_latency_seconds` histogram (+ ttft/itl siblings, buckets 1ms–2560s), and the `strata:*` gauges. Flagger's tiny Prometheus scrapes the web pods via the new `podAnnotations` passthrough (the path annotation carries the `/metrics?format=prometheus` query string; `Accept: text/plain` alone also triggers the format per `wants_prometheus`). The analysis metrics are CUSTOM MetricTemplates — the builtin gatewayapi HttpObserver expects `http_request_duration_seconds_*` (by `kubernetes_namespace`/`kubernetes_pod_name`), which Strata does NOT expose (verified): the finish-rate of `vllm:request_success_total` and the p99 of `vllm:e2e_request_latency_seconds`, with the SAME HttpObserver-style pod-name regex (which matches target AND primary pods — Flagger's documented pod-metric pattern; the mixed measurement is recorded honestly, with the CLEAN canary-only split as the recorded alternative: Traefik's `traefik_service_request_duration_seconds_bucket{service=~"{{ namespace }}-{{ target }}-canary-[0-9a-zA-Z-]+@kubernetescrd"}` — query shape verified from `observers/traefik.go`). The loadtest drives CHAT completions through the gateway (~10 rps POSTs) — the only traffic that finishes engine requests and feeds the counter — making it load-bearing: without it the finish-rate is empty → failed checks → even the good upgrade rolls back. Consistency note: the BROKEN upgrade's metrics stay healthy (the engine works; only the hub config is broken) — the pre-rollout webhook remains the broken upgrade's only tripwire, exactly the gate story. Budget: Traefik + one prometheus pod ≈ +2–3 min — versus the flux2-monitoring-example's kube-prometheus-stack + grafana, owned by the monitoring card for phase 15.
5. **No MetalLB — the gateway is dialed IN-CLUSTER.** Traefik (the ADR-001 production controller) is the Gateway API implementation: the chart's `providers.kubernetesGateway.enabled=true` makes it watch Gateways of `gatewayClassName: traefik` (the chart auto-creates the GatewayClass — ASSERTED at runtime, applied ourselves if missing); the Gateway is referenced by `spec.service.gatewayRefs` (REQUIRED by the gatewayapi provider — verified from the tutorial). Traefik's LoadBalancer Service stays pending on kind — irrelevant: the tutorial's own loadtest dials the gateway's Service DNS from inside the cluster (the dial pattern, not the implementation), which needs only the ClusterIP; the pre-rollout suite targets the app Services directly. Names DERIVED, never assumed: the Traefik Service, the Prometheus Service, the GatewayClass. A pre-canary round-trip smoke through the gateway (`/health` with the route host → 200) proves routing BEFORE the analysis starts. **The remaining `speculation`:** whether Flagger (or Traefik's controller) gates on the Gateway's address/Programmed status — if the canary stalls in Initialized, the fallback ladder is: (1) MetalLB L2 on the kind network (the kind-docs pattern), (2) the Istio-minimal shape from the gatewayapi tutorial (this design's recorded predecessor — its stack is the tutorial verbatim), (3) the canned `vector(1)` MetricTemplate + responder from the first draft (the honest last resort). Each fallback is additive to the same script.
6. **Cilium stays the CNI** (the phase-5 recipe verbatim — `--policy-cidr-match-mode=nodes`): the FULL artifact chain (flux policies + the mcp chart's auto-resolved CNP + `artifact-ingress.yaml`) is proven under Cilium by phase 5; a kindnet variant would re-prove an unproven combination to save ~4 minutes. The chart's `apiServer.mode: auto` resolves either way.
7. **The artifact chain is REUSED BY PATH, not copied.** Phase 5's machinery is merged on main: the rehearsal builds its gittestserver helper, applies the repo-sync test manifests (`gitrepository.yaml`, `artifactgenerator.yaml`, `artifact-ingress.yaml`) and pushes the fixture repo once. Real data flows: `list_tickets` answers with the seed ticket, `repo_facts` reports the artifact revision — the selftest questions get contract answers. The recorded lighter alternative (no artifact; a values override skipping the fetcher's readiness gate) was rejected: it edits the shared mcp chart mid-flight and downgrades the selftest receipts to no-data stubs.
8. **The mcp wiring lives in the Deployment template via a chart knob** (`web.mcpConfig` → inline ConfigMap + mount + arg) — Flagger copies the canary's template from the target, so BOTH versions get the hub config automatically; the hub's URL (`http://chudmax-mcp:8080/mcp`) is release-shape-derived (the umbrella's `fullnameOverride`s pin `chudmax-mcp`; port = the mcp chart's `server.port` 8080). The canonical server has NO Host guard (verified — only optional bearer auth, off here), so the hub's outbound calls need no extra config. Alternative recorded: raw `extraVolumes`/`extraVolumeMounts` passthroughs — rejected: more knobs, the same mount rendered wrong is easier.
9. **`web.service.enabled` (new knob) avoids the Flagger Service collision.** Flagger generates `<name>`, `<name>-canary`, `<name>-primary` Services; the chart's unconditional `chudmax-web` Service would collide. Default true (no default-render change); the canary install sets it false; the test hook gates on it too. **Constraint recorded:** the rehearsal installs ONCE and mutates only with kubectl — a later `helm upgrade` would revert Flagger's template mutations (helm still owns the object).
10. **The pre-rollout suite is jq-free and self-calibrating.** Tool counts compare as **byte-equality of the two `GET /v1/mcp/tools` bodies** (same hub config, same server → identical deterministic JSON) plus grep-presence of the namespaced names — no jq dependency (the loadtester image's toolset is unverified). The selftest questions run through `POST /v1/mcp/call` with namespaced names (`tickets__list_tickets`, `tickets__repo_facts`, `tickets__get_ticket{id: <seed>}`, plus the read-only four asserted non-empty); the seed id is discovered from `list_tickets`' first `T-` line; exact response substrings are pinned from the sandbox pre-flight receipts, never assumed. The suite retries bounded (hub registration is async) and fits under the webhook timeout.
11. **Timing budget.** Two upgrades × (interval-stepping to maxWeight 50 + webhook runs) ≈ 5–7 intervals each at 30s–1m ≈ 10–15 min; cluster + Cilium + flux + images ≈ 8–10 min; Traefik + the tiny Prometheus ≈ 2–3 min; the chain + installs ≈ 5 min → **30–40 min, `timeout-minutes: 75`** (phase 5's 45 was tight without the canary iterations and the gateway). The interval value is an implementation choice (the tutorial uses 1m; the quickstart uses 10s) — recorded in the receipt.
12. **Proofs are object-based PLUS one metric receipt.** The HTTPRoute weight timeline is sampled per interval (`kubectl get httproute chudmax-web -o jsonpath` over `backendRefs[*].weight`); the promotion/rollback are receipted by canary status + events verbatim; both suites' outputs are echoed; and the script instant-queries the tiny Prometheus mid-analysis for `vllm:request_success_total` (rate > 0) and the `vllm:e2e_request_latency_seconds_bucket` series for the target — the receipt that REAL app-native metrics ran, not just that the analysis passed. The "10% at a time to 50%" claim is the weight timeline itself. `speculation` labels only where mechanics are unverified (the Gateway-readiness gate; Traefik's chart value keys + GatewayClass auto-creation — verified against `helm show values`/the cluster at implementation; per-iteration vs once-per-rollout pre-rollout execution — the acceptance asserts are robust to either).

## Notes for future agents (learnings)

- **Spike Open Question 2 (split the largest rehearsal?)** — resolved by the human's default: one card. Open Question 1 surfaces it at review.
- **Spike's "does the fork's hub accept the server by url?"** — settled: YES (`serve/mcp.py` HttpTransport, Streamable HTTP, URL-config entries; public clone @ `de34ebaa…`, tag `v0.2.21-mbp.rtx.1`). The REMAINING unknown is the hub ↔ canonical-server integration (the server is a non-standard one-JSON-per-POST endpoint; the hub tolerates it if it parses the single JSON response — the sandbox pre-flight proves this in userspace, no cluster needed).
- **The silent-omission behavior is the rollback's engine:** a hub config pointing at an unreachable server yields zero tools with the web otherwise healthy — the ONLY deterministic way to make the canary Ready-but-failing so the pre-rollout webhook (not the probe, not the progress deadline) is what catches the broken upgrade.
- **The webhook suite curls Flagger-generated Service names** (`chudmax-web-canary`, `chudmax-web-primary`) — these are NOT in the chart's `allowedHosts: auto` render (the chart does not know Flagger's names) → the rehearsal's explicit `web.allowedHosts` list must include them (a list is used verbatim — the phase-6 short-name lesson applies: same-namespace curls send short names). **The names are DERIVED, not assumed:** Flagger names its Services after the TARGET deployment's fullname — the umbrella's `web.fullnameOverride: chudmax-web` pins it (no release prefix; the brief's `<release>-chudmax-web-*` example is the UNPINNED shape) — the script computes the fullname from the live cluster right after the umbrella install (before Flagger exists) and renders the list (plus the canary's HTTPRoute/Gateway host and loopback), so a naming change upstream cannot silently 403 the suite.
- **`kubectl patch --type=json` with multiple ops in ONE call = ONE template mutation = ONE Flagger revision** — mixing `set image` and a follow-up args patch would create two revisions and race Flagger's detection.
- **The loadtester executes webhook `metadata.cmd` under bash** (`type: bash`); the webhook url follows the tutorial shape `http://<loadtester-release>.<ns>/`; the loadtester must be installed in the release namespace so the suite's short-name curls resolve (and the same-namespace admission keeps the no-NetworkPolicy web reachable).
- **Pins table:** kind v0.33.0; Cilium per phase 5's recipe; flux v2.10.1 (`--components-extra=source-watcher`); flagger + loadtester chart versions pinned at implementation (the tiny Prometheus's image is pinned BY the flagger chart — upgrade it only with the chart); the Traefik chart version pinned at implementation (the ADR's value keys — `providers.kubernetesGateway.enabled`, the metrics entrypoint :9100 — verified against `helm show values` before use, `speculation` until then); the Gateway API CRDs pinned (the tutorial's v1.4.0 suggestion); the Strata image = the phase-6 build at the README pins-table SHA (`de34ebaa…`, tag `v0.2.21-mbp.rtx.1`).
- **kind cannot run in this sandbox** (phase-6 constraint, verbatim reason recorded there) — the sandbox CAN: helm lint/template/kubeconform, image builds, and the userspace pre-flight (both servers on loopback). The kind receipts are CI-authoritative.
- **The no-data trap (why the loadtest is load-bearing):** Flagger's Prometheus provider treats an empty query result as a failed check — the tutorial's rollback demo works because traffic exists throughout. The loadtest stream through the gateway is what makes the metric checks REAL; omit it and even the good upgrade rolls back on empty metrics.
- **The builtin-observer map (verified from `pkg/metrics/observers/factory.go` + the observer sources @ main):** `gatewayapi:v1` (and `kubernetes`) → the **HttpObserver** — builtin `request-success-rate`/`request-duration` query the APP's `http_request_duration_seconds_*` by `kubernetes_namespace` + `kubernetes_pod_name=~"{{ target }}-[0-9a-zA-Z]+(-[0-9a-zA-Z]+)"`; `traefik` → the **TraefikObserver** — the same builtin names but querying `traefik_service_request_duration_seconds_bucket{service=~"{{ namespace }}-{{ target }}-canary-[0-9a-zA-Z-]+@kubernetescrd"}` (which documents Traefik's service-label format AND gives a clean canary-only split — but the `traefik` meshProvider routes via IngressRoutes, NOT the HTTPRoute machinery the card requires — so it stays the recorded alternative, available as custom templates under the gatewayapi provider). Custom MetricTemplates bypass the observer entirely — which is what the rehearsal uses.
- **Strata's native metric set (verified from `terminal/serve/prometheus.py` @ the pin):** `vllm:request_success_total` (counter — finished requests), `vllm:prompt_tokens_total`, `vllm:generation_tokens_total`, `vllm:num_requests_running/waiting`, `vllm:kv_cache_usage_perc`, the histograms `vllm:e2e_request_latency_seconds` / `vllm:time_to_first_token_seconds` / `vllm:inter_token_latency_seconds` (bucket/sum/count), `strata:live_state`, `strata:live_tok_s`, `strata:totals_prompt_seconds_total`, `strata:totals_decode_seconds_total`, the gpu/cpu/ram gauges — labeled `model_name`. The format rule (`wants_prometheus`): `?format=prometheus` OR an `Accept: text/plain`/openmetrics header. **`http_request_duration_seconds_*` is NOT in the set** — the reason the custom templates exist. The sandbox pre-flight receipts: a chat turn increments `vllm:request_success_total` and fills the e2e histogram (the exact de-risking assert for the metric pipeline).
- **Annotation-scrape vs ServiceMonitor — the phase-15 bridge (now two-card):** the tiny Prometheus scrapes by pod annotations (the web pods get theirs via the chart's `podAnnotations` passthrough; Traefik's pods the same way); the monitoring card's kube-prometheus-stack scrapes via ServiceMonitor/PodMonitor CRDs — its PodMonitor for the web selects the SAME `/metrics?format=prometheus` endpoint. Flagger's chart ships both knobs (`serviceMonitor.enabled`/`podMonitor.enabled`, default false). Phase 15: repoint `canary.metricsServer` at the monitoring card's stack endpoint, flip the flagger ServiceMonitor knob, keep the SAME MetricTemplate fixtures (their `provider.address` is envsubst'd from the knob — no fixture edits) — the drop-in compatibility the owner asked for.
- **Hygiene reminders (hard):** no registry push (public images are PULLED, our images are LOADED); RFC 5737 `203.0.113.10` wherever a doc IP is needed; no LAN/credential/internal hostname; three labels on every claim; the mcpConfig's dead-URL fixture uses a never-resolving in-cluster name, not a public IP; the loadtest's route host is a doc hostname (e.g. `chudmax.rehearsal`), never a real domain.
- **Standing facts not to re-litigate:** kindnet HAS enforced NetworkPolicy since kind v0.24 (never write "kindnet enforces no policies" — phases 5/6 corrected this twice); the EndpointSlice address space is IPv4-only (DNS names belong to the legacy-Endpoints alternative); the mcp chart's apiserver key is `networkPolicy.egress.apiServer.cidrs` (a list) since phase 5 — any script still setting singular `cidr` is stale.

## What this settles

- The canary rehearsal story end to end: fixtures, the two upgrades, the gate, the receipts — the largest rehearsal, unsplit.
- The mcp Service's ready-gated path in a rehearsal (phase 6's explicit pointer): the artifact chain ships the seed and the Service serves.
- The hub's URL-mode integration with the canonical server (pre-flight receipt) — phase 15's attach route inherits a proven hub pattern.
- The metric dimension for real, at runner scale: the strata-native metrics via Flagger's single-pod Prometheus + the Traefik gateway per ADR-001, with the custom templates' one-knob provider (`canary.metricsServer`) standing in for the monitoring card's stack — and the fallback ladder (MetalLB / the Istio-tutorial shape / the canned stub) recorded for whatever CI surfaces.
