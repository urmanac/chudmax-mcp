# Design: chudmax k8s phase 9 Hermes chart with persistent home

> **Public mirror** — the full-fidelity record (including deployment specifics) lives in the private source-of-truth repo.

Phase 9 adds the Hermes chart as an installable part and proves it on kind: persistent HERMES_HOME, pod-delete survival, restore onto an empty volume, and a chat served through the mock engine. It builds **no image** — upstream publishes semver-tagged ones — and edits the mcp chart **nowhere**: the NetworkPolicy question is settled by namespace placement. **Steering correction (Gemini brief, 2026-11-26, `handoff-reported` — phases 5 & 6 merged on main @ `0787cfe`):** the chart is staged at `k8s/chart/hermes-agent/` with its own `.github/workflows/hermes-chart.yml`, **the umbrella gets no edits while phase 7 (Flagger canary) runs in parallel** (`k8s/umbrella/`, `k8s/canary/` write-off-limits), the umbrella dep moves to phase 10 with the split to `urmanac/hermes-agent`, and the rehearsal installs the engine/mcp charts **read-only from their in-tree paths** as standalone releases. Requirements in `requirements.md`; the phase-9 row lives in `kubernetes/phases.md` on the private source-of-truth repo (SPIKE row I). All upstream facts were verified against `github.com/NousResearch/hermes-agent` at tag `v0.23.4` and the Docker Hub registry API from this sandbox on 2026-11-26 (`verified-here`).

## The mcp NetworkPolicy question — decided: one shared namespace

The mcp chart's default ingress NetworkPolicy admits TCP to the server port from **the same namespace** (a namespace `podSelector` + `extraIngress` passthrough), and kindnet has **enforced** NetworkPolicy since kind v0.24 — so the proof is real, not assumed. Decision: **the rehearsal installs engine, mcp and hermes into one namespace, so hermes pods are admitted by the existing default rule with zero new configuration** — no extraIngress, no chart edit, nothing rendered. The proof asserts it (a 200 from the hermes pod to the tickets-mcp Service). A **foreign-namespace** hermes install is the documented alternative: it must add the rule itself via the mcp chart's `extraIngress` passthrough — documented in the hermes chart README, never rendered here. Same reasoning as phase 6's no-policies stance: this phase renders no NetworkPolicy on the hermes chart itself (CNI-dependent egress guesses wait for phases 12/15; hermes' real egress — model providers on the internet — is exactly that).

## Key decisions

1. **Upstream image, no build.** `nousresearch/hermes-agent:v0.23.4` (manifest list `sha256:ef0650d5…`, amd64+arm64; `stable` shares the digest; per-arch tags exist for rc/canary builds only — the CI receipt). The `digest` values knob exists because upstream's own docs recommend digest pins for deployments; default stays the readable tag. The community chart (0.8.0, no LICENSE) is rejected on those two facts; upstream's MIT repo + registry-published images need no fork. Consequence: phase 9 has **no image job** — the kind job pre-pulls the upstream image ONTO THE NODE (`crictl pull`, containerd resolving the multi-arch list natively — the production path) and builds only the two mcp-pod images from the repo's existing Dockerfiles (podman first, per standing policy; amd64-only in the rehearsal job — the upstream image's dual-arch needs no local proof).
2. **One Deployment, Recreate — and never runAsNonRoot.** Upstream forbids two gateways on one data directory (concurrent SQLite/session writes), so `strategy: Recreate` with an RWO PVC. The image is **root-then-drop by design**: s6-overlay's `/init` runs `stage2-hook.sh` as root (remaps `HERMES_UID`/`HERMES_GID`, chowns the volume, seeds `.env`/`config.yaml`/`SOUL.md` on first boot, syncs skills) and then every supervised service drops to UID 10000 via `s6-setuidgid`. Forcing `runAsNonRoot: true` (the 4b pattern) would break the stage2 chown window; `capabilities.drop: ALL` would break chown/setuid. The chart therefore applies only `seccompProfile: RuntimeDefault` + `automountServiceAccountToken: false` and documents the deviation loudly — the trust boundary moves to "we trust the upstream image's bootstrap," which is the same trust already extended by consuming the image itself.
3. **The exposed interface is the API server.** `gateway run` (the compose-defined deployment command) with `API_SERVER_ENABLED=true`, `API_SERVER_HOST=0.0.0.0`, `API_SERVER_PORT=8642`, `API_SERVER_KEY` from a Secret. Reasons: it is the only programmatic surface designed for external clients; the bearer key is mandatory upstream (even loopback); `/health` is the public cheap probe route (`/health/detailed` is the authenticated readiness check — not used by probes, documented for operators). The dashboard (`HERMES_DASHBOARD=1`, :9119) and webapp (:9120) fail closed on non-loopback binds without an auth provider — the June 2026 hardening — so they stay off; enabling them is an operator recipe in the README, not a chart default. The TUI/CLI is exec-only (the image's exec shim drops root callers to UID 10000, so `kubectl exec … hermes config set` writes as the right user).
4. **HERMES_HOME = the PVC; the backup story is upstream's own.** Mount the PVC at `/opt/data` (`VOLUME` in the image; `HERMES_HOME` env already points there). Backup/restore uses `hermes backup -o <zip>` / `hermes import <zip>` — the upstream-sanctioned whole-home mechanism (profiles, memory, persona, skills, conversations, scheduled jobs, settings, keys/logins). Documented inventory: state = `.env`, `config.yaml`, `SOUL.md`, `memories/`, `sessions/` + `state.db` + `response_store.db`, `skills/`, `profiles/`, `cron/`, `hooks/`, `skins/`, `home/`, `plugins/`, `auth.json`; regenerable = `cache/` (uv re-seeds), `installs/` (PM re-resolves against each new image at boot), `logs/`. No chart-side snapshot logic — the PVC survives pod deletes (PVC ≠ pod), and import covers the disaster case.
5. **SQLite WAL is safe here.** `state.db` opens in WAL mode; upstream documents corruption only on virtiofs/9p/NFS-class mounts. local-path is node-local ext4 (both kind and the box's provisioner class) → WAL applies unchanged. Documented in the README so nobody "fixes" it later.
6. **Probes from the public route.** Startup/readiness/liveness `httpGet /health:8642` — unauthenticated by design, so no probe needs the key. The API server boots inside the s6 tree (stage2 + config migrations can take tens of seconds) → startup probe with a generous failureThreshold (30 × 10 s). When `apiServer.enabled: false` no probes render (no HTTP surface) — documented, and that mode is not the chart default.
7. **Config injection: none by default; env first, exec second.** Hermes reads config from `$HERMES_HOME/config.yaml` + `.env`; stage2 seeds starters on first boot and never overwrites existing files. The chart does **not** mount `config.yaml` (a ConfigMap mount would collide with Hermes' own config migrations, which write timestamped backups next to the file). Secrets/keys flow via `extraEnv` (direct `-e` overrides `.env`, documented upstream); model-provider config flows via `hermes config set` through exec — in the rehearsal the smoke script does this (provider `custom`, `base_url http://<engine-service>:8080/v1`, key `none`), and real installs repeat it or write `.env` via a Secret. The chart itself stays engine-agnostic — the engine pointer is the rehearsal's wiring, not the chart's. Minimal values is the card's word; this is where it is honored.
8. **No umbrella edits; standalone releases instead.** The engine pointer chart and the mcp chart are installed from their committed in-tree paths (`helm install <name> <path>` — a pure read, like phase 6's `file://` consumption but as separate releases). Release names are chosen so the rendered Service names are the short production-ish names (`chudmax-engine`, `chudmax-mcp`, `hermes`). The umbrella's hermes dependency + `hermes.enabled` block are phase 10's move alongside the split to `urmanac/hermes-agent` — by then the chart directory is a pure move and the umbrella gains one `file://`/OCI dep. If phase 16 starts before phase 10 lands, the dep may need to land early (open question 3 in requirements.md).
9. **The rehearsal's proof sequence** (CI kind job, the authoritative receipt): install → ready (probe) → `config set phase9.marker` + provider config → `hermes backup` + `kubectl cp` the zip out → `kubectl delete pod` → new pod ready → marker survives → uninstall + fresh install (new PVC) → cp zip in → `hermes import` → restart → marker + provider config read back (the restore carried the whole config) → `POST /v1/chat/completions` through the Service with the bearer key → a scripted turn from the mock engine → hermes pod → tickets-mcp Service 200 (admission). Diagnostics honor the phase-6 lessons: Host header on any bridge-facing curl; one-shot pods read via `kubectl logs`, never the attach stream; `-sS -w '%{http_code}'`; assert on logs/answers, never pod status alone (kindnet enforces policies).
10. **Pins and hygiene.** kind v0.33.0, helm 3.16.x, kubeconform (yannh) — the phase-5/6 pins; `curlimages/curl` pinned by tag for the hook; upstream image tag `v0.23.4` + digest recorded in the chart README (the umbrella pins table is phase 10's, not writable now). LICENSE deferred (standing flag, PR-description note); zero LAN IPs (bridge gateway computed at runtime; RFC 5737 in templates if ever needed); box untouched; no registry push.

## Notes for future agents (learnings)

- **Upstream image facts (`verified-here`, v0.23.4):** Debian trixie base; s6-overlay 3.2.3.0 supervision (main-hermes, dashboard, per-profile gateways under `/run/hermes-service/`); UID 10000 default (`HERMES_UID`/`HERMES_GID` remap at boot; `PUID`/`PGID` aliases); `HERMES_HOME=/opt/data` is the `VOLUME`; `/opt/hermes` is the immutable install tree (root-owned, read-only to the runtime user; `hermes update` refuses image-owned code — replace the image); lazy installs land in `/opt/data/installs` (`security.allow_lazy_installs: false` to refuse); provenance at `/etc/hermes/image-provenance.json`; ENTRYPOINT is `entrypoint-dispatch.sh` (PID-1 → full s6; wrapped-PID-1 platforms get a degraded fallback without supervised services — in k8s the container is PID 1, so the full path applies). `CMD []` + `main-wrapper.sh` arg routing: `gateway run` as the chart's args matches the compose deployment pattern.
- **The API-server surface (v0.23.4 docs):** `POST /v1/chat/completions`, `/v1/responses`, `/v1/runs`, `/v1/models`, `/v1/capabilities`, `GET /health` (+`/v1/health`) public, `/health/detailed` authenticated. Key mandatory for every deployment. `API_SERVER_*` are env vars, not `config.yaml` keys (per-profile keys live in each profile's `.env`).
- **The Host-guard lesson transfers:** any curl against the bridge mock needs `Host: <engine-service-name>`; hermes' own requests carry the Service DNS name naturally, so the config-driven path is the honest probe.
- **kubectl exec drops to UID 10000** via the image's `/opt/hermes/bin/hermes` shim — backup zips, config writes and imports from exec land with the right ownership; opt out only with `HERMES_DOCKER_EXEC_AS_ROOT=1` (never needed here).
- **Standalone-release mechanics:** installing a chart from a path is a read of that path — the phase-6 `file://` pattern without the umbrella; release-name choice controls the rendered Service DNS names (pick short names so the base_url and admission rules read naturally). If the engine subchart's path moves before this phase lands, render its Service + EndpointSlice in the smoke script instead (recorded fallback).
- **Sandbox constraints:** kind cannot run in this sandbox (rootless docker, ro cgroup2 — phase 6's finding); local proofs are helm lint/template/kubeconform only; the kind job in CI is authoritative (the established precedent). The image is large — budget CI time for the pull; label the timing `speculation` until the first green run.
- **Labels:** upstream research and local renders are `verified-here`; the kind receipts are `speculation` until the CI run greens them (then re-label in proofs.md); the Gemini brief's decisions are `handoff-reported`.
- **Do not resurrect:** the community chart (no license, targets 0.8.0); a `runAsNonRoot` securityContext on this pod; a mounted `config.yaml`; a chart-side backup job (upstream's `hermes backup` is the mechanism); any edit to the mcp chart for admission; any edit under `k8s/umbrella/` while phase 7 is active.

## Implementation notes (2026-11-26, sandbox — all `verified-here`)

- **Toolchain:** helm 3.16.4 + kubeconform 0.6.7 installed to `~/.local/bin` — `/usr/local/bin` is NOT writable in this sandbox (the phase-3 recipe's `mv /usr/local/bin` fails here; adjust the recipe). kind/kubectl/docker present but the daemon is rootless — kind still cannot run here (the phase-6 finding re-confirmed). No podman needed locally: phase 9 builds nothing.
- **The write set held:** exactly `k8s/chart/hermes-agent/**` (7 files + kind-smoke.sh) + `.github/workflows/hermes-chart.yml`. `k8s/umbrella/`, `k8s/canary/` (not yet on main), phase-7 workflows, the mcp chart, the root README — all untouched; the engine subchart + the mcp chart are consumed read-only (install-from-path in the rehearsal).
- **Two authoring bugs caught by the local battery (why the negative tests matter):** (1) `automountServiceAccountToken` was silently absent from values.yaml — the deployment rendered the key EMPTY (`automountServiceAccountToken:` with no value) and kubeconform did NOT flag it — only a parsed-render check caught it; (2) the first python shape-check tripped on document order — helm sorts rendered manifests by KIND (Secret first), so any per-kind assertion must select by kind, never by document position.
- **The guard negative test works in `helm lint` too:** bare-defaults lint/template both fail loudly with the guard message; the workflow asserts the failure (`if template; then error`). Documented in the workflow header so nobody "fixes" the lint red on defaults.
- **Test-hook pin aligned to the repo:** `curlimages/curl:8.12.1` (the engine subchart's existing pin), not 8.11.1 — one curl image across the effort.
- **Engine-subchart keys verified before use (don't guess):** `fullnameOverride`, `service.port` (8080), `endpoint.host`/`endpoint.port` (EndpointSlice rendered only when host set), and its own `test-health.yaml` hook that curls the SHORT service name (`http://chudmax-engine:8080/health` → Host `chudmax-engine:8080` — the mock's guard strips the port and allows the short name, so `helm test engine` works against the bridge mock with `STRATA_ALLOWED_HOSTS=chudmax-engine,…`).
- **Rehearsal-script decisions worth keeping:** release names are short (`engine`/`mcp`/`hermes` with `fullnameOverride` = the short production-ish names); the admission proof targets the mcp POD IP (the Service has no endpoints pre-artifact — the phase-6 lesson) and asserts the mcp ingress NetworkPolicy's same-namespace rule; the empty-volume proof asserts the PVC's `volumeName` CHANGES across the uninstall/reinstall (helm uninstall deletes release PVCs — verified behavior assumption labeled for first-run confirmation); `hermes import` tries the plain form first and falls back to `--force` (the stage2-seeded starter files may collide with a strict import); the chat proof rides a `kubectl port-forward` through the Service with the bearer key and greps the mock's scripted `Hello from the mock engine` turn.
- **kind-smoke.sh lives in the chart dir** (the umbrella precedent — `k8s/umbrella/chudmax/kind-smoke.sh`); helm lint ignores it; it gets packaged into the chart tarball harmlessly.

## Implementation notes (2026-11-26, CI incidents #1 and #2 — all `verified-here` via the public API/annotations)

- **Run #1 (2m25s):** the `chart` job GREEN (all eight steps; the local receipts held in CI); the `kind` job failed in the smoke's image section — the manifest-list pull succeeded (digest `sha256:ef0650d5…`, the recorded v0.23.4 list) but `kind load docker-image` failed: `ctr: content digest sha256:2223ae…: not found` — the arm64 instance blob, which the docker daemon never pulled; ctr's `--all-platforms` import aborts on the first missing blob.
- **Run #2 (57s):** the attempted fix (pull the per-arch tag `v0.23.4-amd64`, re-tag, load) died at the pull — **`v0.23.4-amd64` is not pullable**: the per-arch tags exist for rc/canary builds only; the final release publishes only list tags. The earlier "per-arch (`v0.23.4-amd64`/`-arm64`)" claim is corrected in requirements/design.
- **The settled route (9ac4e24): pre-pull ON THE NODE via `crictl pull`** (`docker exec <cluster>-control-plane crictl pull <image>`) — containerd resolves the multi-arch list natively (exactly what a real install does), no docker-daemon intermediary, no archive shuffling; fallback = the kubelet's own pull under `pullPolicy: IfNotPresent`. Learning for any multi-arch image in a kind rehearsal: **do not route through the runner's docker daemon** (`kind load docker-image` cannot import a list whose blobs the daemon lacks, and the per-arch tags may not exist); let the node's containerd pull.
- The receipt plumbing worked as designed both runs: the run-summary page and annotations carried the error lines; the anonymous API (jobs endpoint) exposed the failing step precisely.

## What this settles

- The three questions the card posed are answered with receipts: upstream publishes semver multi-arch images (consume `v0.23.4`); the interface is the keyed OpenAI-compatible API server on 8642; the backup inventory is the whole home minus `cache/`, `installs/`, `logs/` with `hermes backup`/`import` as the mechanism.
- The mcp-chart admission question is settled by placement (one shared namespace) and proven by assertion, with the foreign-namespace recipe documented; the engine is reached by hermes' own model-provider config, keeping the chart engine-agnostic.
- Still `speculation` after this spec: hermes' custom-provider shape against the Strata mock's `/v1/chat/completions`; CI pull/load timing for the ~1.15 GB image; `hermes import` accepting a live-gateway restart cadence — first exercised in the implementation run, re-labeled from evidence.
