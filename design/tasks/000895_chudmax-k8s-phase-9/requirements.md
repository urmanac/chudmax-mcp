## The three questions, answered

1. **Does upstream publish a semver-tagged multi-arch image? Yes.** Docker Hub `nousresearch/hermes-agent` publishes immutable version tags as multi-arch (amd64+arm64) manifest lists — `v0.23.4` pushed 2026-11-24, manifest-list digest `sha256:ef0650d5…` (slim) and `v0.23.4-desktop` digest `sha256:d7f13dd6…` — plus channel tags `stable` (= the `v0.23.4` digest), `latest`, `main`, `canary.<stamp>-vX.Y.Z` and rc tags (`rc.2-v0.23.4`). Per-arch tags exist **for rc/canary builds only** (`rc.2-v0.23.4-amd64`, `canary.<stamp>-v0.23.4-amd64` — the CI receipt, run #2: the final release publishes only list tags; `v0.23.4-amd64` is not pullable). The v0.23.4 tree carries the Dockerfile and the s6-overlay supervision layout; the release path publishes tested, never-rebuilt archives. The chart therefore consumes `nousresearch/hermes-agent:v0.23.4` directly — **no image is built in this phase** (podman/multi-arch build rules only engage if a wrapper image ever appears; the upstream image is already both arches). The chart carries a digest-pinning knob (upstream docs: "use a digest for an exact deployment pin").
2. **Which interface do we expose? The OpenAI-compatible API server on port 8642** — the one programmatic HTTP surface designed for external clients (Open WebUI, LobeChat, any `/v1/` client), gated by `API_SERVER_ENABLED=true` + `API_SERVER_HOST=0.0.0.0` + a mandatory `API_SERVER_KEY` (min 8 chars, required for every deployment), with an **unauthenticated `GET /health`** for probes. The dashboard (9119) and the webapp (9120) are browser surfaces that **fail closed** on non-loopback binds without an auth provider (the June 2026 hardening — an unauthenticated dashboard was the entry point of the MCP-config persistence campaign) — chart-default **off**, documented knobs. The TUI/CLI is interactive only: reached via `kubectl exec` (the image's exec shim drops to UID 10000), never a Service. The messaging gateway (Telegram etc.) is an egress surface, not an ingress one — nothing to expose.
3. **What exactly in HERMES_HOME must be backed up/restored?** `HERMES_HOME` is `/opt/data` in the container (`~/.hermes` on a host install). **State that must survive: the whole agent home minus the regenerable trio.** Sanctioned mechanism (used by the proof): `hermes backup -o <zip>` → `hermes import <zip>` — the upstream backup captures "the whole Hermes home: every profile, memory, persona, skills, conversations, scheduled jobs, settings, and your keys and logins (`.env`, `auth.json`)". Inventory: `.env`, `config.yaml`, `SOUL.md`, `memories/` (USER.md, MEMORY.md), `sessions/` + `state.db` (SQLite, WAL) + `response_store.db`, `skills/`, `profiles/` (incl. per-profile `.env` and `gateway_state.json`), `cron/`, `hooks/`, `skins/`, `home/` (per-profile HOME for tool subprocesses — `.ssh`, `.gitconfig`, skill-CLI credentials), `plugins/`, `auth.json`. **Regenerable, not backed up:** `cache/` (uv cache re-seeded from the image), `installs/` (PM dependency generations re-resolved at boot against the new image's lock), `logs/` (runtime).

## User stories

1. **As the human**, I want the Hermes chart to consume the upstream semver-tagged multi-arch image (`nousresearch/hermes-agent:v0.23.4`) so chudmax's agent rides upstream releases instead of a fork we maintain — with a digest knob for exact pins, and the community chart's non-license recorded as the reason we didn't take it.
2. **As the human**, I want exactly one HTTP surface exposed — the keyed OpenAI-compatible API server on 8642 — because that is the interface chudmax's ecosystem (and phase 16's "answering from chudmax's model") actually speaks, while the auth-gated dashboard/webapp stay off by default and the TUI stays reachable only by exec.
3. **As the human**, I want HERMES_HOME on a PVC (local-path in rehearsal) that survives a pod delete, and a documented backup/restore story (`hermes backup` → `hermes import`) proven onto an empty volume — so an agent's soul, memory, sessions, skills and credentials outlive any pod.
4. **As the rehearsal**, I want a standalone kind install — the engine pointer chart and the mcp chart installed read-only from their in-tree paths, hermes beside them, **all in one namespace** — with hermes configured (rehearsal-only) to answer through the engine Service, and a chat completion through the hermes API server to return the mock engine's scripted turn: the production shape (pod → Service → external engine) exercised end to end.
5. **As the rehearsal**, I want the mcp chart's default ingress NetworkPolicy to admit hermes **by construction** — same-namespace pods are admitted — with a proof (a 200 from the hermes pod to the tickets-mcp Service) and no edits to the mcp chart; the hermes chart README documents the standalone-install admission recipe.
6. **As CI**, I want `hermes-chart.yml` to re-prove everything: lint/template/kubeconform (defaults + rehearsal variant), the standalone kind install, the pod-delete survival, the restore-onto-empty-volume, the mock-engine chat, and the mcp-admission check — while every phase-7 workflow stays green and untouched.
7. **As the human**, I want the standing hygiene: box untouched, no registry push, no credential or LAN address in any public artifact (the API key is a rehearsal-only non-secret in CI values, real keys enter via Secrets at placement), three labels on every claim, conventional commits, merge authority CoS.
