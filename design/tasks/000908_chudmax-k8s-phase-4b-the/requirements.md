## User stories

1. **As a user installing the chart**, I follow the chart README's optional-server example, which points at the mock image, and get a working MCP server container out of the box — a real example of the bring-your-own interface instead of a placeholder.
2. **As an MCP client author**, I can drive the mock over stdio or HTTP and exercise the same seven read-only tools, the same `initialize`/`tools/list`/`tools/call` shapes, and the same HTTP semantics (one JSON object per POST to `/mcp`, 202 empty for notifications, 405 for GET, 400 for malformed) that the canonical server speaks.
3. **As the phase-5 rehearsal**, I deploy the mock as the server under test: the fetcher swaps `/data/current`, and the mock's `repo_facts` answers from `/data/current/artifact.json` read per call — no restart, no git — while its tool answers look exactly like the canonical's would.
4. **As the owner**, I want the mock's fixture data obviously synthetic (a few mock tickets, a mock STATE.md, a couple of mock docs/decisions records), so the public repo stays public-safe by construction — no original tickets, no LAN addresses, no credential names, no proxy hostnames.
5. **As CI**, I want every push to re-prove the mock: tests over both transports, a both-arches image build alongside the fetcher image (no push), and a chart template with the example values.

## Acceptance criteria

- [ ] `k8s/tickets-mcp-mock/` ships the mock server as a fresh, single-file Python 3 stdlib program (no dependencies, no copied code text from the private repo) plus its mock fixture and a test suite that drives BOTH transports.
- [ ] Signature-compatible with the canonical: the same seven tools (names, order, inputSchemas — including the load-bearing `default N` max_chars descriptions), the same `initialize` result (`protocolVersion: 2024-11-05`, `capabilities.tools.listChanged: false`, `serverInfo.name: "chudmax-tickets"` mirrored verbatim — the canonical selftest asserts it), `tools/list` and `resources/list` both answering `{"tools": [...]}`, `tools/call` returning text content blocks (unknown tool → `isError: true`; exceptions become `error: …` text, never killing the pipe), unknown method → `-32601`, notifications getting no stdio reply. HTTP: POST → one JSON object (200), notification (no `id`) → **202 with an empty body**, GET → **405** with `Allow: POST`, malformed body → **400** with `-32700`, startup printing `listening on <host>:<port>`. stdio: one JSON-RPC object per line; blank and unparsable lines skipped silently.
- [ ] Pod mode: started with `--data-root <root>`, every `repo_facts` call reads `<root>/current/artifact.json` fresh through the symlink and reports url, revision, digest, produced, unpacked, source (plus ticket counts); ticket/doc tools read the unpacked tree through `current` per call. A test builds a fixture volume root (revision dir + `current` symlink + artifact.json), swaps the symlink mid-run, and proves the next call reports the new facts — no restart. The canonical's phase-1 flags (`--revision/--artifact-produced/--artifact-unpacked`) stay accepted for CLI parity (the canonical selftest's pod-mode shape); `--data-root` wins when both are given.
- [ ] The mock's fixture is its own, in the canonical `tickets.md` grammar (`## T-XXXX - Title`, `**Status/Owner/Priority/…:**`, `**Purpose:**`, diary entries): a few mock tickets across several statuses (one long enough to exercise `get_ticket`'s middle-trim), a mock `STATE.md`, a couple of mock docs and decisions records. Zero original-repo tickets; zero LAN addresses, credential names, or proxy hostnames; a hygiene test asserts the denylist.
- [ ] Tests mirror the canonical selftest's proven style — real subprocess over stdio, real loopback HTTP, results keyed by call (not by tool name) — covering all seven tools over both transports, the 202/405/400 semantics, trim-note behavior (middle for tickets, end for docs), the advertised-default cross-check, and `repo_facts` against a fixture `artifact.json`.
- [ ] One OCI image builds as a manifest list for `linux/amd64` and `linux/arm64` under podman (COPY-only Dockerfile → no emulation), runs non-root, defaults to stdio over the bundled fixture; built in CI alongside the fetcher image; **no registry push**.
- [ ] The chart README (`k8s/chart/chudmax-mcp/README.md`, created — docs-only, chart behavior unchanged) documents the optional-server example values pointing at the mock image (`ghcr.io/urmanac/chudmax/tickets-mcp-mock:0.1.0`, unpublished until phase 10 — build-it-yourself note), HTTP mode on `server.port`, and `--data-root /data`; CI templates that example; `helm lint`/`template` stay green.
- [ ] CI: the mock's test suite runs (Python job); the mock image builds both arches and gets an HTTP smoke (initialize 200, notification 202, GET 405, malformed 400); the chart job templates the mock example. Existing jobs stay green.
- [ ] The root README's "Bring your own MCP server" section points at the chart README's example; the mock dir has its own README (what it is, what it is not — no real data; the canonical stays private).
- [ ] Delivery flow: branch off public `main` (`67d8616`), conventional commits, three labels on every claim, box untouched, PR via `propose_pull_request` (no approval wait), CI green + in-sandbox verification before merge, merge authority CoS/owner, `mark_task_complete` only after merge; the missing-LICENSE flag rides along in the PR description (phase-3 precedent).
